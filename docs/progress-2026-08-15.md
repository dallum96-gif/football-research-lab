## Performance fix

The 2025–26 path was causing a major performance regression because the seasonal team-code/identity lookup was being rebuilt repeatedly. Caching `_verified_team_names(season)` removed that repeated work.

Observed before optimisation:

- 2016–17 → 2025–26: ~28.5 seconds
- 2016–17 → 2024–25: ~3.1 seconds

After caching, the player tests ran substantially faster while preserving the same research result.

Known longitudinal smoke-test result:

- Erling Haaland, 2021–22 → 2025–26: 5 seasons, 13,776 minutes, 148 goals.
- Erling Haaland, 2016–17 → 2025–26 query: 4,172 player identities; Haaland still resolves to the same 5-season result.

## GUI checkpoint

The large attempted native Streamlit multipage redesign was **not adopted as the stable state**. The monolithic legacy app was restored because automatically extracting the existing tab blocks caused indentation/runtime regressions and several new page modules were incomplete relative to the original screens.

Current direction:

- Keep the known-good app as the reference implementation.
- Do not perform further bulk rewrites of the monolithic `gui/app.py`.
- Build the next radical UI overhaul with stronger repo-level editing/tooling available.
- Preserve existing screen behaviour while separating presentation from the research/query layer.

## Current Player Research UI direction

The Player Research screen has been iterated toward:

1. Player Research heading first.
2. Research scope beneath the heading.
3. Single season / Multiple seasons mode.
4. From/To selectors for longitudinal research.
5. Player search/position/club/minutes filters underneath scope.
6. Statistical conditions below the basic filters.
7. Results and player detail after the query controls.

Integer statistics such as Minutes, Goals, Assists, BPS, and FPL points should use integer inputs/display rather than decimal-number controls.

## Next major UI goal

A radical UI overhaul is desired. The target interaction model is:

- left navigation organised around Explore / Research / Modelling / Evidence
- Player Research as the showcase workspace
- compact research scope controls
- a real condition builder rather than “Number of filters”
- prominent, clean result tables
- player profiles that feel analytical rather than database-like
- evidence/provenance available without dominating the main interface

Do not sacrifice the 26/26 research contract while changing the presentation layer.

## Working principle

Use the Risk Strategy Framework proactively:

- foresee likely failure modes before implementation
- preserve a known-good rollback point
- keep data/research semantics separate from GUI experiments
- compile/test candidates before replacing trusted code
- use a fast regression gate for UI-only work
- run the full 26/26 gate after research-engine changes and before a release checkpoint
